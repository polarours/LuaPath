# 热路径上的全局查找

## 错误

在性能关键的循环里访问全局变量（经过环境表查找）比访问局部变量更慢。

## 复现

```lua
-- 慢：每次迭代都要做全局查找
for i = 1, 1000000 do
  local x = math.sin(i)  -- 先查 "math"，再查 "sin"
end

-- 快：缓存到局部
local sin = math.sin
for i = 1, 1000000 do
  local x = sin(i)  -- 直接读 VM 寄存器
end
```

## 为什么是错的

一次全局访问要付出两次表查找——先查环境表，再查其中的字段；而局部变量
本来就躺在 VM 寄存器里。

这个收益是真实的，但幅度有限，值得说清楚到底有多有限。对一个空函数
做两千万次调用，一次走全局、一次走局部，大致是这样：

| 运行时 | 全局 | 局部 | 比值 |
|---|---|---|---|
| Lua 5.1 | 0.308 s | 0.248 s | 1.24x |
| Lua 5.3 | 0.278 s | 0.219 s | 1.27x |
| Lua 5.4 | 0.220 s | 0.172 s | 1.28x |
| Lua 5.5 | 0.258 s | 0.175 s | 1.47x |
| LuaJIT 2.1 | 0.006 s | 0.005 s | 1.04x |

也就是说，在参考解释器上，一次全局调用大约比同样的局部调用贵四分之一到一半；
而在 LuaJIT 上这个差别几乎完全消失，因为 JIT 会把全局查找提到循环之外。

还要注意，在一个把时间都花在 `math.sin` 上的循环里，一次查找只占很小一部分成本。
缓存查找值得做，但别指望它单独就能改变一份性能剖析的形状。

## 修复

```lua
-- 在模块作用域缓存全局
local sin = math.sin
local cos = math.cos
local sqrt = math.sqrt
local max = math.max
local min = math.min

local function compute(x, y)
  return sqrt(sin(x)^2 + cos(y)^2)
end
```

## 核心要点

把频繁使用的全局缓存成模块作用域的局部变量。这件事不花任何代价，在解释器上
大约能省下四分之一的调用开销——不过 LuaJIT 本来就替你做了。
